# 源代码阅读方法调研

> 调研对象：`python_projects/archery-mcp`
>
> 调研日期：2026-09-23
>
> 目的：把“读代码”从逐行浏览，变成一套可以复现、验证和记忆的工作流。

## 1. 结论先行

阅读陌生代码时，最有效的顺序不是从第一行读到最后一行，而是依次回答六个问题：

1. **它对外承诺什么？**——命令、API、MCP tool、输入、输出和副作用是什么。
2. **程序从哪里启动？**——找到入口，再沿一条真实用例追踪调用链。
3. **数据经过了哪些形状变化？**——例如 `str → dict → Response → dict`，而不是只记函数名。
4. **状态和失败路径在哪里？**——缓存、重试、超时、权限、异常和降级分支通常比主路径更值得读。
5. **这个实现为什么会这样写？**——用 Git 历史确认设计动机，不要把当前代码当成永恒真理。
6. **我能否不看代码重新讲出来？**——用预测、画图、复述和小实验检验“看懂”的感觉。

因此，源码阅读的产物不应是“我看过哪些文件”，而应是：

- 一张入口和模块地图；
- 一条带数据形状的主调用链；
- 一张分支、状态和错误清单；
- 一组能够证伪自己理解的实验或测试；
- 一段合上代码后仍能复述的说明。

## 2. 证据来源与适用范围

### 2.1 项目自身是第一手证据

本次对 `archery-mcp` 的判断主要来自以下文件：

- [`README.md`](../../python_projects/archery-mcp/README.md)：用户可见的启动方式、命令和配置位置。
- [`pyproject.toml`](../../python_projects/archery-mcp/pyproject.toml)：Python 版本、依赖和 `archery-sql-mcp` 的脚本入口。
- [`archery_sql_mcp/__init__.py`](../../python_projects/archery-mcp/archery_sql_mcp/__init__.py)：运行时真实行为。
- [`TODO.md`](../../python_projects/archery-mcp/TODO.md)：作者明确留下的拆分计划。
- Git 历史：初始实现和后续配置目录迁移。

文档只能说明“项目希望如何被使用”；函数体、异常路径和实际配置读取逻辑才是判断“项目实际上怎么工作”的主要依据。阅读时发生冲突，应把冲突记录下来，而不是默默选择其中一个说法。

### 2.2 工具文档能说明工具的观察边界

以下一手资料支持本文的方法，但不替代对项目源码的阅读：

- Python [`ast`](https://docs.python.org/3/library/ast.html)：Python 源码可以被解析为抽象语法树，适合快速获取模块、类、函数和装饰器结构；它能告诉我们“代码长什么样”，不能单独告诉我们运行时数据如何流动。
- Python [`pdb`](https://docs.python.org/3/library/pdb.html)：支持源码级断点、单步执行、查看栈帧，适合验证一条动态调用链。
- Python [`trace`](https://docs.python.org/3/library/trace.html)：可以跟踪语句执行，生成覆盖率信息，并显示 caller/callee 关系；适合验证“实际走了哪条路径”，不适合代替设计理解。
- Git [`log`](https://git-scm.com/docs/git-log)：通过提交历史和 `--follow` 追踪文件演化。
- Git [`blame`](https://git-scm.com/docs/git-blame)：显示某一行最后由哪个修订和作者修改；它是定位历史入口，不是判断代码质量的工具。
- Git [`bisect`](https://git-scm.com/docs/git-bisect)：用二分搜索定位引入回归的提交，前提是已有可靠的“好/坏”判定。
- Python [`pyproject.toml` specification](https://packaging.python.org/en/latest/specifications/pyproject-toml/)：说明 `[project]` 元数据和脚本入口的声明位置。
- MCP [`stdio transport`](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)：规定 MCP stdio 服务端从 stdin 读取 JSON-RPC、向 stdout 写消息，并且 stdout 不能混入非 MCP 消息；这直接决定了阅读 MCP 入口时必须检查输出行为。

### 2.3 记忆方法的证据

源码阅读中加入“先预测、再打开实现、最后对照”的原因，不是为了增加仪式感，而是为了制造主动回忆。Roediger 与 Karpicke 的原始研究：[*Test-Enhanced Learning*](https://doi.org/10.1111/j.1467-9280.2006.01693.x)，研究主题是测试本身如何改善长期保持。

这项研究支持“读完后主动回忆和自测通常比继续重复阅读更有价值”这一学习策略；它不等于证明某一种具体源码阅读模板对所有人都最优，所以本文把它作为学习机制依据，而不是把它当作工程规范。

## 3. 推荐工作流：契约 → 数据流 → 调用链 → 分支 → 验证 → 回忆

### 阶段一：先建立外部契约

先读 README、构建配置和入口配置，不要马上钻进实现细节。记录：

| 项目 | 要回答的问题 |
|---|---|
| 启动方式 | 无参数、子命令、脚本入口分别做什么？ |
| 输入 | 参数、环境变量、配置文件、stdin、远程响应分别是什么？ |
| 输出 | 人读文本、JSON、协议消息还是退出码？ |
| 副作用 | 写哪些本地文件？调用哪些外部服务？是否修改远程数据？ |
| 依赖 | 哪些库决定了运行时边界？ |
| 安全边界 | 哪一层做权限和危险操作拦截？ |

对 `archery-mcp` 而言，`pyproject.toml` 中的：

```toml
[project.scripts]
archery-sql-mcp = "archery_sql_mcp:main"
```

说明 CLI 入口是 `archery_sql_mcp.main`。README 进一步说明：无参数启动是 MCP stdio，带子命令时是 CLI。于是阅读入口的第一站应是 `main()`，而不是文件顶部的常量。

### 阶段二：从入口画一张最小地图

只记录“能到达的主要节点”，暂时不记每一行：

```text
main()
├── 无 command
│   └── run_mcp()
│       ├── query
│       ├── query_redis
│       ├── get_token
│       ├── refresh_token
│       ├── list_instances
│       └── instance_resources
└── 有 command
    ├── init
    ├── check
    ├── query
    ├── redis
    ├── instances
    └── install-mcp
```

这张图先回答“系统由哪些入口组成”，不试图解释每个函数的内部实现。

### 阶段三：选择一条真实用例，标出数据形状

选最有业务价值、同时能穿过最多层的用例。例如：

```text
命令行字符串
  ↓
argparse.Namespace
  ↓
配置 dict
  ↓
SQL 字符串 + 请求参数 dict
  ↓
httpx.Response
  ↓
JSON payload dict
  ↓
标准化结果 dict
  ↓
JSON 文本或 MCP tool 返回值
```

对每个箭头补上三个问题：

1. 谁创建了这个值？
2. 谁修改或校验了它？
3. 如果它不符合预期，错误在哪里产生？

这一步能避免只记住“有一个 query 函数”，却说不清它怎样变成远程 HTTP 请求和最终结果。

### 阶段四：按调用链精读，而不是按文件顺序精读

`archery-mcp` 的 SQL 主链适合按以下顺序阅读：

1. `main()`：CLI 分发和无参数转 MCP。
2. `run_mcp()`：MCP 工具的输入、输出和异常投影。
3. `cmd_query()`：CLI 参数如何传入公共客户端。
4. `load_profile()`：默认值、profile、环境变量的合并优先级。
5. `ArcheryClient.query()`：SQL 校验、提交、同步/异步结果分支。
6. `_authed()`：带 session 的请求和失效重试。
7. `SessionManager.ensure()` / `login()`：磁盘缓存、CSRF 和登录协议。
8. `query_redis()`、`list_instances()`、`instance_resources()`：复用哪些公共边界，哪些接口行为不同。
9. `install_mcp()`：最后阅读与业务查询无关的客户端配置写入逻辑。

如果中途发现函数依赖了尚未理解的对象，只回溯到能解释当前调用的一层，不要顺手把整个文件全部读完。

### 阶段五：专门寻找状态机和失败路径

主路径通常很容易读懂，真正决定可靠性的往往是分支：

- 配置文件不存在、JSON 损坏、profile 不存在时怎么办？
- session 缓存存在但已失效时怎么办？
- 登录返回 JSON 失败和旧式 302 行为时怎么办？
- `/query/` 直接返回 rows 与返回 query_id 时怎么办？
- 查询进入 `failed`、`aborted` 或超时时怎么办？
- SQL 或 Redis 命令被客户端拦截时怎么办？
- MCP 调用失败时，异常是抛出、转成 JSON，还是变成普通字符串？

建议用一张表记录，而不是只在脑中记忆：

| 状态/异常 | 触发点 | 处理动作 | 是否重试 | 对外结果 |
|---|---|---|---|---|
| 没有 session | `ensure()` | 从缓存加载或登录 | 登录一次 | 继续请求或报错 |
| 302 到登录页 | `_authed()` | 清除缓存并重登 | 最多重放一次 | 失败后抛 `ArcheryError` |
| 同步查询 | `/query/` 返回 rows | 直接标准化结果 | 否 | finished |
| 异步查询 | `/query/` 返回 query_id | 轮询 `/queryresult/` | 按间隔轮询 | finished/失败/超时 |
| 违规 SQL | `_check_sql_allowed()` | 本地拒绝 | 否 | 调用方收到错误 |

### 阶段六：用 Git 历史解释“为什么”

当前代码的历史规模不大，可以直接运行：

```bash
git -C python_projects log --follow --oneline -- archery-mcp/archery_sql_mcp/__init__.py
git -C python_projects log -p -- archery-mcp/archery_sql_mcp/__init__.py
git -C python_projects blame -- archery-mcp/archery_sql_mcp/__init__.py
```

适用原则：

- `git log --follow`：看文件整体如何演化，尤其适合追踪重命名或迁移。
- `git log -p`：针对一个设计点看修改前后，而不是把全部历史当小说读。
- `git blame -L 起始行,结束行`：从一段可疑代码定位相关提交。
- `git bisect`：只有出现可重复回归、并且能可靠判断好坏时才使用。

对 `archery-mcp` 来说，历史能帮助确认：项目先有单文件初始实现，后来增加了统一数据根目录；因此 README、模块注释和 MCP docstring 出现路径不一致并不奇怪，这属于需要记录的文档漂移。

### 阶段七：用工具验证假设

静态阅读之后，优先验证低风险、可重复的部分：

#### 1. 用 `ast` 获取结构

```bash
python -c "import ast, pathlib; p=pathlib.Path('python_projects/archery-mcp/archery_sql_mcp/__init__.py'); t=ast.parse(p.read_text(encoding='utf-8')); print([(type(n).__name__, getattr(n, 'name', None), getattr(n, 'lineno', None)) for n in t.body if isinstance(n, (ast.FunctionDef, ast.AsyncFunctionDef, ast.ClassDef))])"
```

它适合确认顶层结构和行号，不适合证明函数一定会被调用。

#### 2. 用 `pdb` 验证局部调用

对于不需要生产凭据的纯函数，可以在本地构造输入后使用 `breakpoint()` 或 `python -m pdb`，观察参数和返回值。不要为了调试本工具而直接触发线上查询。

#### 3. 用 `trace` 观察实际路径

在隔离的本地测试或 mock 环境中使用 `trace`，可以确认同步分支、异步轮询分支和错误分支是否真的经过预期函数。它只能记录发生了什么，不能替代对未执行分支的静态分析。

#### 4. 用测试固定行为

如果项目开始拆分，应优先为不接触生产服务的边界补测试：

- `load_profile()` 的配置优先级；
- `_check_sql_allowed()` 的合法与非法输入；
- `SessionManager.is_expired()` 的 302 判定；
- 同步结果、异步轮询、超时和失败响应的标准化；
- `_json_upsert()` / `_toml_upsert()` 是否保留已有配置。

测试应使用 fake response 或 mock HTTP，不应把真实账号、密码、session 或生产 Redis 放进测试。

### 阶段八：合上代码做主动回忆

阅读一个函数后，先关闭文件，再回答：

- 输入的类型和边界是什么？
- 我会如何实现？
- 作者额外处理了哪个我没想到的情况？
- 失败时返回什么？
- 哪个外部契约限制了这个实现？

阅读完一条主链后，凭记忆重画数据流，并把每条箭头标成具体形状。如果只能写“数据传过去了”，说明还没有真正掌握。

## 4. 应用于 `archery-mcp` 的具体阅读练习

### 练习 A：入口地图

不看实现，只根据 `README.md` 和 `pyproject.toml` 写出：

- 无参数启动做什么；
- `query`、`redis`、`check`、`install-mcp` 分别属于哪层；
- MCP 和 CLI 是否共享查询实现。

然后打开 `main()`、`run_mcp()` 和各个 `cmd_*` 函数核对。

### 练习 B：预测 SQL 守卫

在打开 `_check_sql_allowed()` 之前，预测以下输入的结果：

```sql
SELECT 1
WITH x AS (SELECT 1) SELECT * FROM x
UPDATE t SET x = 1
SELECT 1; SELECT 2
SELECT INTO new_table FROM old_table
WITH x AS (DELETE FROM t RETURNING *) SELECT * FROM x
```

再对照实现，记录三类差异：

- 预测正确：已有知识；
- 预测错误：需要精读；
- 作者处理了但自己没想到：最值得形成个人检查清单。

特别注意：当前实现使用正则和首词判断，并不是完整 SQL parser；“客户端拒绝了常见写操作”不能推导出“任意 SQL 都被安全解析”。

### 练习 C：凭记忆画查询链

合上代码，画出：

```text
SQL
 → 校验
 → 登录态准备
 → POST /query/
 → 同步结果 / query_id
 → 轮询
 → 标准化结果
 → CLI JSON / MCP 字符串
```

然后补三条支线：

- session 失效后的重新登录与重放；
- 查询失败或超时；
- 配置和账号缺失。

### 练习 D：MCP stdio 边界

先读 MCP stdio 规范，再检查 `run_mcp()`：

- 工具函数返回的是 JSON 文本还是 Python 对象？
- 错误是抛出还是序列化为 `{"error": ...}`？
- 运行期间是否有普通 `print()` 可能污染 stdout？
- CLI 的人读输出和 MCP 的协议输出是否被分开？

这类检查比只确认“注册了几个 tool”更重要，因为 MCP 客户端依赖传输层契约。

## 5. 本项目的阅读结论与风险清单

### 已确认的结构事实

- 项目是一个远程 Archery HTTP 适配器，不是数据库驱动。
- 公共核心主要是 `SessionManager` 和 `ArcheryClient`。
- CLI 和 MCP 都会在调用时加载配置，并把查询结果转换为 JSON。
- 查询支持同步和异步两种 Archery 平台响应模式。
- Redis 和 SQL 都通过 Archery 的 `/query/` 入口提交，但采用不同的客户端前置校验。
- `install_mcp()` 是配置适配逻辑，与数据库查询主链相对独立。

### 阅读时不能直接假设的事情

- “只读”不能只由客户端黑名单证明，仍需确认 Archery 服务端权限。
- “session 缓存存在”不能证明 session 有效，必须看 302 失效处理。
- “MCP tool 返回 JSON 字符串”不能自动等同于结构化 MCP 内容，需要结合 SDK 和协议行为确认。
- “没有测试目录”不能证明代码没有被验证过，只能证明当前仓库没有可见的自动化测试入口。
- “模块注释写的配置路径”不能覆盖实际常量定义和 README 中的当前路径。

### 维护者下一步最值得补的验证

1. 把单文件拆成配置、认证、客户端、CLI、MCP 适配几个模块，但先保持行为不变。
2. 为 SQL/Redis 守卫增加明确的单元测试，并把“客户端预检不是安全边界”写入文档。
3. 为同步和异步查询响应构造 fake HTTP 测试，覆盖重登、失败和超时。
4. 统一 README、模块 docstring、MCP docstring 中的配置路径。
5. 为 MCP 返回结果明确选择字符串 JSON 还是 SDK 支持的结构化返回，并补协议级验证。
6. 避免在真实生产账号下做源码阅读实验；把所有动态验证放到 mock 或隔离环境。
