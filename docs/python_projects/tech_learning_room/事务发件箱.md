# transactional_outbox —— 数据库与消息系统的一致性

> 代码：`apps/transactional_outbox` ｜ 依赖：PostgreSQL（前 3 个场景无需 Kafka；kafka-e2e 场景需 Kafka）

## 一、这组实验解决什么问题

「订单落库后发一条 Kafka 通知库存服务」——这句需求里藏着分布式系统最经典的裂缝：**数据库事务与消息通道是两个独立系统，不存在跨两者的原子提交**。无论先做哪一步，另一步都可能失败。发件箱（Outbox）模式是工程上的标准答案，本组实验从双写的两个故障窗口开始，完整走一遍「同事务写入 → 租约领取 → 崩溃重投 → 消费幂等」的闭环。

## 二、核心原理

### 2.1 双写问题的两个窗口

```
窗口 A（先提交后发送）：           窗口 B（先发送后提交）：
  BEGIN                             BEGIN
    INSERT order                     INSERT order
  COMMIT          ← 成功             发送消息     ← 成功
  发送消息        ← 失败！           COMMIT       ← 崩溃回滚！
  结果：事件永久丢失                 结果：幽灵事件（下游收到不存在的订单）
```

两个方向的失败模式互补：A 丢事件、B 产幽灵。**换顺序解决不了问题，因为问题在「跨系统原子性」本身。**

### 2.2 发件箱：把消息变成数据库行

解法是把「发消息」降级为「写数据库」：

```
BEGIN
  INSERT order
  INSERT outbox (event)    ← 同一个事务
COMMIT
```

事件与业务状态**原子一致**（同生共死）。投递器（dispatcher）作为独立进程把 outbox 行搬运到真正的消息系统——数据库是「真相源」，消息只是投递格式。

### 2.3 投递器：短事务领取 + 租约 + 退避

投递循环三段式（连接池友好：任何阶段都不长时间持有连接）：

1. **事务 1（短）**：`SELECT ... WHERE status='pending' FOR UPDATE SKIP LOCKED LIMIT n` → 置 `leased` + 租约 token → commit。`SKIP LOCKED` 让多个投递器并行领取互不阻塞；
2. **发送**（不持有任何数据库连接）：调 Kafka producer；
3. **事务 2（短）**：成功 → 置 `sent`；失败 → 回 `pending` + 退避时间，重试超上限 → `dead`（死信，人工处理）。

**租约（lease）的意义**：投递器崩溃在「发送成功但未标记」之间时，行停在 `leased`；租约到期后被恢复任务放回 `pending` 重新投递——于是**同一条消息可能被发送两次**。

### 2.4 至少一次 + 消费幂等 = 恰好一次的工程等效

重复投递不可避免（崩溃重投、rebalance 重放、生产者重试），工程目标从「不重复」降级为「重复无害」：

- 消息携带全局唯一 `message_id`；
- 消费端：**幂等标记与业务写同一事务**——先查标记，已处理则直接 ack（duplicate），否则业务写 + 插标记一起 commit。

处理失败时不留标记，消息可安全重投。

## 三、场景详解

| 场景 | 依赖 | 演示 |
|---|---|---|
| dual-write-problem | 仅 PG | 两个窗口逐一复现：丢事件 / 幽灵事件 |
| outbox-atomic | 仅 PG | 正常路径订单+outbox 同提交；失败路径（写入后业务校验失败）两表零残留 |
| dispatcher-crash | 仅 PG | 注入「发送成功后、标记前崩溃」→ 租约到期恢复 → 重发（通道里同 message_id 两条）→ 消费端 processed/duplicate |
| kafka-e2e | PG + Kafka | 真实 producer（acks=all）→ consumer 拉取 → 幂等消费闭环 |

## 五、面试高频问答

- **Q：为什么不用「本地消息表 + 定时扫描」的说法？** A：是同一个模式的不同叫法；关键点不在名字，而在「同事务写入」与「领取后如何处理崩溃」。
- **Q：SKIP LOCKED 的作用？** A：多投递器并行领取时跳过已被锁的行，避免互相等待——把「抢占」变成「自然分工」。
- **Q：为什么需要租约，直接 pending 到 sent 两态不行吗？** A：投递器领走行后崩溃，行若已置「发送中」却无人恢复就永远卡住；租约给了「超时自动归还」的机制。与分布式锁的租约是同一思想（见 [redis-cache-consistency](Redis 缓存一致性.md) 场景 5）。
- **Q：消息已经发出去但标记 sent 失败，消费者会收到两次，怎么办？** A：这正是「至少一次」的来源，靠消费幂等收敛。不要试图在发送端消灭重复（不可能），要在消费端让重复无害。
- **Q：outbox 表会越来越大？** A：已 sent 的行定期归档/清理（或分区表按时间切）；dead 行需要告警 + 人工重放通道。
- **Q：和 CDC（Debezium/binlog 订阅）比呢？** A：CDC 从 binlog 捕获 outbox 表变更，投递延迟更低、不轮询数据库；代价是多一套基础设施。自研轮询版胜在零依赖、行为完全可控。

## 六、生产对照（creativault）

生产实现完整复刻了本骨架：outbox 与业务写同事务、`outbox_dispatch_task` 用 `FOR UPDATE SKIP LOCKED` 多 worker 并行、`2^attempt` 指数退避超 8 次置 dead、事件名「聚合名+过去式」39 条契约常量。教学版把 Kafka 抽象成 Transport 协议（内存实现可注入故障 + 真实现走 aiokafka），核心逻辑一份代码两种通道。
