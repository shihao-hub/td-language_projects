# 05 评测方法

对应实验：`apps/eval_lab`。没有评测的微调是玄学——「感觉变好了」不算证据。

```powershell
uv run python -m apps.eval_lab --scenario run --model qwen3-4b --load 4bit --adapter <adapter路径> --tag qlora4b
uv run python -m apps.eval_lab --scenario compare --model qwen3-4b --load 4bit --adapter <adapter路径> --sample 100
```

## 一、评测什么：四个指标

| 指标 | 含义 | 训练坏了的典型症状 |
|---|---|---|
| QA 准确率 | 文档内问题答对比例（correct+partial） | 覆盖不足 / 过拟合背题 |
| 拒答正确率 | 越界问题正确说「未找到」的比例 | refusal 样本太少 |
| 幻觉率 | 越界问题却编出条款的比例 | **强约束场景最致命的指标** |
| 该答不答率 | 文档有规定却拒答 | refusal 样本太多（冒烟测试的翻车现场） |

## 二、两阶段流程：为什么生成和判分必须分开

被测模型（占 4-6GB 显存）和 Ollama 裁判（qwen2.5:7b 占 ~5GB）**在同一块 8GB 卡上不能共存**。所以：

```
阶段 1：被测模型逐题生成 → 全部答完 → del + empty_cache 释放显存
阶段 2：Ollama 裁判逐题判分 → 汇总
```

## 三、LLM-as-judge 的边界

裁判 prompt 给出四档判定（correct/partial/wrong/refused），裁判本身也是模型——**7B 裁判对「部分正确」的尺度偏松**。两个补救：

1. refusal 类不走裁判：拒答话术是训练时写死的（「未找到相关规定」），关键词匹配即可判定，零成本零误判；
2. 重要结论用 `eval_details.md` 人工复核 wrong 样本——那里藏着最有价值的 bad case。

## 四、对比基线怎么选

`compare` 场景跑「base+system prompt vs 微调」两个 tag。微调的**真正价值**通常不在 QA 准确率（那更多靠模型能力），而在：

- 拒答正确率：base 模型再强的 system prompt 也压不住它「热心解答」的预训练倾向
- 幻觉率：base 遇到不知道的制度问题会编一个像模像样的条款号

QA 准确率的天花板受限于 4B 模型的记忆容量——这正是实验 07（RAG）要解决的。

## 五、产出物

- `outputs/eval/<tag>/eval_report.json`：指标汇总（进 git 之外的报告目录，可多 tag 横比）
- `outputs/eval/<tag>/eval_details.md`：逐题明细（问题/参考/模型答案/判定/理由）
