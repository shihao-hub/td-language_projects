# TaskbarGuard v3 架构调研报告

> 调研日期：2026-10-06。范围：`go_projects/taskbarguard` v3 架构改造（service 分层 + 多壳入口 + 嵌入式原生 web + `--json`/`--schema` 契约）。
> 体例：凡标注 `路径:行号` 或 URL 的为**事实**（有出处）；标注「**建议**」的为基于事实的**推断**，供决策参考。

## TL;DR

1. **方向正确**：提案「service 层包所有业务逻辑 + http/cli/mcp 薄壳直调 + web 走 http」与现行《CLI 工具开发标准》v1 的「Service 核心 + 多壳」最高纲领完全一致；本仓已有两个可直接照抄的落地范式：**sourcecount**（v1 进程内直调，含 contract 契约层与同源 schema 导出）与 **plansql**（v2 daemon 形态，含嵌入式 web 看板）。
2. **taskbarguard 现状离提案很远**：全部业务逻辑（脚本发现、补丁编排、配置读写、schema 目录）都写在 `main.go` 的 CLI 函数里，无 service/http/web/mcp 分层（`go_projects/taskbarguard/main.go:89-544`）。
3. **`--schema` 的 Go 落地**：本仓惯例是 `github.com/google/jsonschema-go`（MCP go-sdk v1.8.0 的传递依赖，`jsonschema.For[T]()` 反射生成，与 pydantic `model_json_schema()` 等价），不引入 invopop/jsonschema；契约单一事实源放在 MCP 工具类型定义上，CLI `schema` 经 in-memory transport 同源导出（sourcecount/agyquota 已验证的模式）。
4. **v3 建议采用 v1 直调形态**（单 exe、cli/http/mcp 各自直调 service、`serve` 子命令按需起 http 供 web 看板），daemon 化（plansql 的 v2 形态）留作后续演进；GUI 若做常驻托盘，参照 glmquotawatch-gui 直调 service 并内嵌 http。
5. **两个现状问题顺带必须修**：`config.json` 落在当前工作目录违反仓库数据目录强约束（须迁 `%APPDATA%\language_projects\taskbarguard\[dev|prod]\`）；`install-task` 注册的计划任务命令是 `list` 而非守护动作（`main.go:231`）。

## 2. 现状盘点：taskbarguard 当前架构与差距

### 2.1 逐文件盘点

| 文件 | 内容 | 分层归属判定 |
|---|---|---|
| `main.go`（559 行） | 唯一源文件：命令分发、全部业务逻辑、JSON/schema 输出、参数归一化 | 业务与壳完全混合 |

| `build.py` | 双轨构建，`-ldflags` 注入 `main.version`/`main.commitHash`（`build.py:42`） | 无 dev/prod 数据目录隔离注入 |

| `README.md` / `TASK_SCHEDULER.md` | 使用说明与计划任务管理手册、守护设计铁律 | 文档（按仓库约定后续镜像到父仓） |

### 2.2 关键事实（引用）

1. **业务逻辑全部在 CLI 函数体内**：脚本发现 `discoverApps`/`findApp`/`inspectApp` 在 `main.go:399-464`；补丁编排 `runPatch`（校验 + 款式回退 + 组装 `uv run` 命令）在 `main.go:148-211`；配置回退逻辑直接读 `config.Apps`（`main.go:171-180`）。业务函数直接持有 `stdout/stderr io.Writer` 并输出（如 `main.go:143,209`），无法脱离 CLI 测试。
2. **执行器是全局可替换变量**：`var commandRunner = func(...)`（`main.go:78-83`），测试靠换全局变量打桩（`main_test.go:58-67`）——功能可用，但属于隐藏全局状态，标准要求「组装入口：不受控的全局可变状态」应避免（`CLI 工具开发标准.md:189`）。
3. **`apply` 在进程内递归调用 `runPatch`**：`applyConfig` 拼子命令 flag 再调 `runPatch(command[1:], ...)`（`main.go:336-348`），把「CLI 解析层」当成了「业务编排层」的复用手段——这正是业务逻辑未下沉导致的典型绕行（标准禁止「绕过用例做编排」的变体，`CLI 工具开发标准.md:186`）。
4. **已有 `--json` 包络与业务错误雏形**：`output{OK,Data,Err}` 与 `cliError{Code,Message}`（`main.go:62-71`）形状符合标准包络（`CLI 工具开发标准.md:274-289`）；但多数失败分支直接把 `err.Error()` 原文当 message（如 `main.go:137`），错误分类不稳定。
5. **`--schema` 是手写字符串目录，非 JSON Schema**：`writeSchema`（`main.go:475-488`）与 `writeCommandSchema`（`main.go:490-528`）输出 `{"--json":"boolean"}` 风格的简化描述，与实际类型无任何同源校验；已正确声明 `"interface": "cli"`（`main.go:477`），符合无 MCP 项目的导出约定（`CLI 工具开发标准.md:384`）。零 I/O 约束已有测试保护（`main_test.go:34-42`）。
6. **`install-task` 注册的计划任务跑的是 `list`**：`"/TR", fmt.Sprintf("\"%s\" list", executable)`（`main.go:231`），与 TASK_SCHEDULER.md 的守护设计（登录时校验并恢复，`TASK_SCHEDULER.md:92-94`）不符，应为占位实现。
7. **配置文件违反数据目录强约束**：`defaultConfigFile = "config.json"` 写 CWD（`config.go:10`；README 明示「CLI 默认在当前工作目录读写 config.json」，`README.md:27`）；父仓 AGENTS.md 要求自有数据只放 `%APPDATA%\language_projects\<项目名>\`，且产 exe 的 dev/prod 构建还须子目录隔离。
8. **阶段 B 已有规划**：main.go 头部注释明确「阶段 B: Go //go:embed 编译全套 .ico 与注入工具，化为纯绿色免安装单文件二进制」（`main.go:30-31`）——嵌入静态资源与「单 exe」是项目既定方向。
9. **v2/v3 演进语境**：`docs/plans/34-taskbarguard-config-and-build.md` 为阶段一（配置持久化 + 双轨构建），4 个 Task 已全部完成（该文件 Task 1-4 均勾选）；阶段二（计划任务守护巡检 + Toast 通知）按用户要求暂缓（`34-taskbarguard-config-and-build.md:11`）。本次 v3 架构改造即承接该语境的下一阶段。

### 2.3 差距总结

提案五入口（service/http/cli/web/gui/mcp）中，taskbarguard 目前只有「cli（且业务混杂）」一项；config.go 可视为 service 层的第一块砖。无 http、无 web、无 gui、无 mcp、无 contract 契约层。

## 4. 外部技术调研（官方一手资料）

### 4.1 Go embed（静态资源嵌入）

来源：<https://pkg.go.dev/embed>

- 三种嵌入类型：`string`、`[]byte`、`embed.FS`；`//go:embed` 指令必须 `import "embed"`（不用 FS 时空白导入）。
- 目录递归嵌入：「all files in the subtree rooted at that directory are embedded (recursively)」；默认排除 `.` 与 `_` 开头的文件，`all:` 前缀可包含它们。
- 模式限制：不得含 `.`/`..`、不得越出模块（如 `.git/*`、符号链接、`vendor/`）；路径分隔符在 Windows 上也用 `/`。
- `embed.FS` 是只读集合，并发安全，「implements fs.FS, so it can be used with any package that understands file system interfaces, including net/http, text/template, and html/template」。
- 官方静态服务示例：`http.Handle("/static/", http.StripPrefix("/static/", http.FileServer(http.FS(content))))`。

对 taskbarguard 的含义（**建议**）：`internal/web/static/` 放原生 html/css/js 用 `//go:embed static` 嵌入即可；阶段 B 的 `.ico/.py` 资产同理（`.py` 脚本可嵌入后释放到 `%APPDATA%` 数据目录或临时目录再执行，实现免 uv 依赖尚需另案评估 Python 运行时问题——`.ico` 是纯数据可直接嵌入读取，`.py` 的执行仍依赖 uv/Python，此为阶段 B 的独立课题）。

### 4.2 Go 1.22+ net/http ServeMux 方法路由

来源：<https://go.dev/blog/routing-enhancements>（taskbarguard go.mod 为 go 1.25.3，可用）

- 方法路由：`mux.HandleFunc("GET /api/items", h)`；「As a special case, GET also matches HEAD」；路径命中但方法不匹配时返回 405 并带 `Allow` 头。
- 路径通配符：`{name}` 单段、`{path...}` 多段、`{$}` 精确尾段；`req.PathValue("name")` 取值。
- 尾斜杠模式是子树前缀匹配；优先级「the most specific pattern wins」，注册冲突会 panic。
- 本仓实证：liteconf 的 `NewMux` 用 `"GET /api/{app}/{env}"`、`"PUT /api/{app}/{env}"`、`r.PathValue("app")`（`go_projects/liteconf/internal/server/handler.go:22-38`）。

**建议**：v3 的 http 壳用标准库 ServeMux 方法路由即可，无需引入第三方路由库（保持零多余依赖）。

### 4.3 Go 侧 JSON Schema 生成（pydantic `model_json_schema()` 的等价物）

两个候选，结论先给：**建议沿用 `github.com/google/jsonschema-go`，不引入 invopop/jsonschema**。

**候选 A：`github.com/google/jsonschema-go`（本仓既有惯例）**

- 事实：本仓 5 个项目（agyquota、clictl、liteconf、plansql、sourcecount）的 go.mod 均因 MCP go-sdk v1.8.0 传递依赖 `google/jsonschema-go v0.4.3`，其中 agyquota 直接 require（`go_projects/agyquota/go.mod`）。
- 事实：核心 API 为 `jsonschema.For[T]()` / `ForType`，从 Go 类型反射生成 JSON Schema（本机 module cache `google/jsonschema-go@v0.4.3/jsonschema/infer.go:44-81`）。翻译规则：struct → `type:"object"` 且 `additionalProperties:false`；`omitempty`/`omitzero` 字段为可选、其余为 required；**「A jsonschema tag on a field is used as the description for the corresponding property」**（`infer.go:80-81`）。README 三大能力「creating schemas, validating JSON values against a schema, and inferring a schema from a Go struct」（`google/jsonschema-go@v0.4.3/README.md:2-4`）。零非标准库依赖，MIT。
- 事实：MCP go-sdk v1.8.0 的泛型 `AddTool` 内部即用它自动推导 schema——`toolForErr` 调 `setSchema[In](&tt.InputSchema, ...)`、`setSchema[Out](&tt.OutputSchema, ...)`（本机 `go-sdk@v1.8.0/mcp/server.go:365-393`），文档注明「the tool's input schema and output schema are automatically populated」（<https://pkg.go.dev/github.com/modelcontextprotocol/go-sdk/mcp>）。
- 含义（**建议**）：用同一套带 `jsonschema` tag 的类型既注册 MCP 工具又导出 CLI `--schema`，天然同源，零新增依赖。

**候选 B：`github.com/invopop/jsonschema`（社区流行款）**

- 事实：alecthomas/jsonschema 的 fork，Draft 2020-12；`Reflect(v any) *Schema` + `Reflector` 配置（`DoNotReference`、`ExpandedStruct`、`RequiredFromJSONSchemaTags` 等）；支持 `jsonschema:"title=...,description=...,example=..."` 富 tag 与 `AddGoComments`（从注释生成 description）；约 1330 个包导入，v0.14.0（2026-04-23），仍处 v0「breaking changes are likely」。来源：<https://pkg.go.dev/github.com/invopop/jsonschema>。
- 对比结论（**建议**）：invopop 功能更全（enum/example/注释提取），但会新增一个 v0 阶段直接依赖；taskbarguard 的 schema 需求（字段类型 + 中文 description + required）`jsonschema.For` 已完全覆盖，且与 MCP SDK 同引擎。除非未来需要 `$ref` 精细控制或注释驱动文档，否则无引入必要。

**手写 vs 反射**：现状手写目录（`main.go:490-528`）与类型零关联，违反标准「避免……独立漂移」（`CLI 工具开发标准.md:138-140`）。**建议 v3 全部改为反射生成**；唯一保留手写的场景是描述 flag 形态 CLI 参数到 DTO 字段映射的那层帮助文本（不属于 JSON Schema 范畴）。

### 4.4 MCP 官方 Go SDK（tool handler 调 service 层）

来源：<https://pkg.go.dev/github.com/modelcontextprotocol/go-sdk/mcp>（v1.8.0）+ 本机 SDK 源码。

- Server/Client：`mcp.NewServer(&mcp.Implementation{...}, nil)`；泛型工具注册 `func AddTool[In, Out any](s *Server, t *Tool, h ToolHandlerFor[In, Out])`，handler 签名 `func(ctx, *CallToolRequest, In) (*CallToolResult, Out, error)`——第三返回值非 nil 即工具失败；In/Out 的 schema 自动生成。
- 传输：`&mcp.StdioTransport{}`（本地默认）；`mcp.NewInMemoryTransports()` 用于测试与离线 schema 导出；客户端 `ListTools` 分页列举。
- handler 内调 service 的官方模式即「handler 只做参数转接 → 调用业务 → 装配 `CallToolResult`」。本仓实证（sourcecount）：`mcp.AddTool(server, &mcp.Tool{...}, func(ctx, req, in scanInput) (...) { out, err := svc.Scan(ctx, contract.ScanRequest{...}) ... })`（`go_projects/sourcecount/internal/mcp/tools.go:24-40`）——input 类型字段与 contract DTO 一一映射，handler 零业务逻辑。
- schema 同源导出的官方姿势：in-memory transport 连接后 `clientSession.ListTools`（agyquota `internal/mcp/schema.go:6-33`、sourcecount `internal/mcp/schema.go:8-33`，注释明言「与协议完全同源……零值 Config 下不触达 daemon、不触发业务网络调用」）。
- 协议基线注意（**建议 v3 实施时核对**）：标准将 go-sdk v1.8.0 落地的项目登记为「存量基线 2025-11-25」（`CLI 工具开发标准.md:64`）；新设计 MCP 能力默认按「当前基线 2026-07-28」设计，SDK 是否支持须按 §10.2.1 升级前三件事核对（`:611-615`），并在能力表登记「协议基线 + SDK 版本 + 已验证客户端」三件套（`:612`）。

### 4.5 GUI 直调 service vs 走 HTTP（可选项）

外部通用资料此轮未取到可用一手页面（wails.io 抓取失败），改用仓库内一手实证，依据充分：

- 事实：v1 标准架构图中 GUI 适配器与 CLI/MCP 并列，「调用用例」直连 Service（`CLI 工具开发标准.md:148-177`）；v1 明言「复用现有业务边界，不在本地重新实现远程规则；上图不要求核心必须处于同一进程」（`:179`）——即直调与 HTTP 都是标准允许形态。
- 事实（直调实证）：glmquotawatch-gui（Wails v3 + 托盘常驻）的 `internal/service/service.go` 包注释：「承载 glmquotawatch-gui 的业务用例……**不做任何标准流输出与 os.Exit——GUI 绑定层与 CLI 壳共用本包，是唯一业务真相源**」（`go_projects/glmquotawatch-gui/internal/service/service.go:1-4`）；Wails 绑定层「全部方法只做参数转发与结果装配，业务规则在 service 层」（`internal/guiapp/bindings.go:1-6`）；通知等副作用经 `Notifier` 接口注入（GUI 注入 Wails 适配器，`service.go:34-37`）——这是「GUI 进程内直调 service + 副作用注入」的完整范本。
- 事实（HTTP 实证）：plansql 的 GUI 等价物是嵌入式 web 看板，走 daemon HTTP API（`go_projects/plansql/internal/daemon/server.go:101-102`）；liteconf 同（webui 挂 `GET /ui/`，`liteconf/internal/server/handler.go:37`）。
- 事实（v2 的取舍理由）：daemon 唯一契约的价值在「业务逻辑只存在一份编译产物，杜绝多产物漂移」与「CLI 与 GUI 并存时天然共享 daemon 的状态、缓存与会话」（`CLI 工具开发标准 v2.md:42,72`）。

## 5. 提案评估：service 层包所有 + 各入口薄壳是否合理

### 5.1 总体判断：合理，且是标准的强制要求；但需先做 v1/v2 形态选型

「service 层包所有业务逻辑」不是可选项，而是 v1 标准的「绝对铁律」（`CLI 工具开发标准.md:21`）。真正需要决策的是**壳与 service 的连接方式**：

| 形态 | 壳如何到达 service | 本仓实证 | 适用前提 |
|---|---|---|---|
| **v1 多壳直调** | cli/mcp/http(gui) 各自 import service 包，进程内调用 | sourcecount、clictl、agyquota、glmquotawatch-gui | 单次执行为主、轻状态、无跨进程共享状态刚需 |
| **v2 daemon 薄壳** | service 只编译进 daemon；cli/gui/mcp 全走 HTTP | plansql、liteconf | 常驻状态（SQLite/WAL、长连接）、多壳并发共享、第三方要写客户端 |

**建议：taskbarguard v3 采用 v1 直调形态**，理由（推断，基于以下事实）：

1. taskbarguard 的状态只有一份低频读写的 `config.json`（`config.go:10-66`），补丁执行是一次性子进程调度（`main.go:203`），没有 plansql 那种 WAL/内存 store 常驻状态（`plansql/internal/daemon/server.go:58-68`）需要跨壳共享；
2. 项目价值主张是「纯绿色免安装单文件二进制」（`main.go:31`），v1 直调天然单 exe；v2 的自动拉起、地址文件、buildID 握手、空闲退出是为一类问题付出的复杂度（`CLI 工具开发标准 v2.md:54-120`），当前需求撑不起；
3. v2 自身定位「探索迭代中（试点标准）——非现行标准」（`CLI 工具开发标准 v2.md:3`），v1 头部要求冲突时回到 v1 裁决（`CLI 工具开发标准.md:8`）；
4. 用户提案原文「http/ 只调用 service 接口然后处理错误；cli/ 也是调用 service」描述的正是 v1 直调形态（http 与 cli 平级），v3 落地它与提案字面一致。

daemon 化留作后续演进触发条件（**建议**）：出现常驻守护进程持有内存状态（阶段二的巡检 + Toast 通知若做成常驻）、或多壳并发写状态产生真实冲突时，再按 v2 迁移（plansql 已提供全部参考代码）。

### 5.2 逐入口分析

**http/** —— **调 service**（正确，无争议）。
- 职责：路由注册、请求解码 → 组装 service 请求 DTO → 调用 → 响应编码（标准 JSON 包络 + 恰当 HTTP status）、错误映射（`CLI 工具开发标准.md:47`）。
- 实证：plansql handler 模式「`s.store.GetAllItems()` → `writeJSON(w, 200, APIResponse{OK:true, Data: items})`，错误走 `APIResponse{OK:false, Error:...}` + 4xx/5xx」（`plansql/internal/daemon/handlers.go:9-35`）；liteconf 更完整：错误分类映射 status（`liteconf/internal/server/handler.go:43-77`）。注意 plansql 的 `APIResponse.Error` 是裸 string（`handlers.go:12`），**建议** taskbarguard 沿用 v1 包络的 `error.code/message` 结构而非裸 string，保持与 CLI `--json` 完全同构（v2 标准也要求「daemon API 的 JSON 设计沿用 v1 包络」，`CLI 工具开发标准 v2.md:145`）。
- 启动形态：`taskbarguard serve --addr 127.0.0.1:<port>` 显式子命令，默认只绑回环地址（本地管理面）。**不做 v2 式自动拉起**（推断：看板属按需能力，标准 `:52`）。

**cli/** —— **调 service**（同上）。
- 职责三段：flag/位置参数解析 → service 调用 → 人读/JSON 渲染 + 退出码映射（0/2/1）。现状 `runPatch` 内的校验、款式回退、脚本组装全部下沉 service，CLI 只留 flag 定义与输出。
- `apply` 的进程内递归调用（`main.go:348`）改由 service 层复用「单应用补丁」用例，CLI 不再拼子命令。

**web/** —— **只能走 http**（提案正确）。
- 浏览器无法进程内调 Go；静态资源 embed 后由 http 壳托管，页面 `fetch('/api/v1/...')`。
- 实证：plansql 看板（`plansql/internal/web/static/index.html + app.js + style.css`，经 `/` 挂载）与 liteconf 控制台（`/ui/` 挂载 + noCache 中间件）。liteconf 的 webui 包注释明确职责铁律：「只做只读托管与渲染，不包含任何存储、校验、版本管理等业务逻辑（业务一律走 /api/*）」（`liteconf/internal/server/webui/webui.go:1-3`）。

**gui/** —— **建议直调 service**（回答提案的问号）。
- 若 gui 与 cli 同属一个 exe（v3 单二进制）：直调是最短路径，标准架构图即如此（`CLI 工具开发标准.md:168`）。
- **常驻托盘场景**（关键差异点）：托盘进程本身就是 service 的宿主进程——gui 直调 service 没有任何问题（glmquotawatch-gui 托盘常驻即此形态，`guiapp/tray.go` + `service/daemon.go`）；此时若还需要 web 看板，由托盘进程内嵌 http server（复用 http 壳的 mux），webview/浏览器走 http——**gui 直调与 web 走 http 并存，不冲突**。
- 并发注意（**建议**）：托盘常驻进程与一次性 CLI 命令可能并发读写 `config.json`，须在存储层用原子写（临时文件 + rename）或文件锁解决；这不足以成为引入 daemon 的理由（配置写入频率极低），但必须写进用例契约（标准要求「项目必须说明……共享状态保护方式」，`:417`）。
- 现实取舍（**建议**）：taskbarguard 的可视化需求（配置管理 + 应用/款式列表 + 一键 apply）用一个嵌入式 web 页面即可满足，v3 不必做原生 GUI；若未来做托盘（阶段二 Toast 通知方向），glmquotawatch-gui 是完整范本（含 dev/prod 数据目录隔离、单例互斥、开机自启注册表保护等仓库硬约束的现成实现，见父仓 AGENTS.md「go_projects」节）。

**mcp/** —— **调 service**（v1 形态下）。
- `<prog> mcp` 起 stdio server，`AddTool` 泛型 handler 直调 service——sourcecount 是标准范本（`sourcecount/internal/mcp/tools.go:24-40`）。
- 仅当采用 v2 daemon 形态时，MCP 才作为「桥」走 HTTP（`CLI 工具开发标准 v2.md:49-51`；plansql 实证 `internal/mcp/server.go:30-45` 经 `cli.NewClient` 发 HTTP）。v3 选 v1 直调，故 mcp 直调 service。
- 工具命名按三段式对齐 CLI 子命令路径（标准 `:325`）：`list` → `taskbarguard.list`（无资源段退化两段）、`run` → `taskbarguard.run`、配置类可设计 `taskbarguard.app.set` 等；能力表须登记协议基线与 SDK 版本三件套（`:612`）。

### 5.3 权衡矩阵（事实依据见括号）

| 维度 | v1 直调（建议） | v2 daemon 薄壳 |
|---|---|---|
| 单二进制 | 天然单 exe，所有壳编译在一起 | 单 exe 双角色，需 serve/拉起/地址文件机制（`v2.md:54-82`；plansql `cli/client.go:56-101`） |
| 端口冲突 | 仅 `serve` 运行期占用端口，按需启动 | daemon 常驻占端口，需地址文件发现 + 拉起互斥（`v2.md:70-72`） |
| 错误一致性 | service 稳定错误一次定义，cli/http/mcp 各自映射（sourcecount `service.Error` 不带退出码，`sourcecount/internal/service/server.go:18-27`） | 同左，但多一层 HTTP 状态码穿透（plansql 的 Error 裸 string 是前车之鉴） |
| 可测试性 | service 可完全绕过入口单测（标准 `:462`「不经过入口也能验证业务规则」） | 需起 daemon 或 mock HTTP；测试链路更长 |
| 跨壳共享状态 | 无共享内存状态时无损失；有则靠存储层并发控制 | 天然共享 daemon 状态（taskbarguard 当前无此需求） |
| 复杂度 | 低，与提案字面一致 | 高（buildID 握手、空闲退出、开发双终端纪律） |

### 5.4 关于「每个 go projects 默认嵌入原生 html css js」的通盘愿景

事实：v1 标准对 GUI/HTTP 入口的定语是「按需」——「存在真实 GUI/HTTP 需求时，再增加相应入口」（`:52`），交付基线不强制 web。v2 daemon 标准则把 web 看板作为形态标配（plansql、liteconf 均带）。
**建议**：「默认嵌入」作为各项目的可选基线能力推广时，宜在标准层面先补一条修订（把「按需」改为「默认提供、记录例外」，或维持 v1 并逐项目登记理由），避免项目实践与标准文本漂移；对 taskbarguard 本身，用户提案已构成明确需求，v3 落地 web 无争议。

## 6. `--schema` 的 Go 落地方案与 `--json` 输出契约

### 6.1 方案（建议）

1. **契约单一事实源**：`internal/contract` 包定义每个用例的 Request/Result DTO，字段带 `json` + `jsonschema`（中文 description）tag——照 sourcecount（`sourcecount/internal/contract/types.go:1-13`：`Roots []string \`json:"roots,omitempty" jsonschema:"扫描根路径；缺省为当前工作目录"\``）。
2. **MCP 工具类型复用同一 DTO（或字段级映射的 input 结构）**：`AddTool` 的 In/Out 经 SDK 自动生成 schema（`go-sdk@v1.8.0/mcp/server.go:365-393`），与手写零关联。
3. **CLI `schema` 同源导出**：经 in-memory transport `ListTools` 取真实工具定义输出目录 `{"name","version","tools":[...]}`（agyquota `internal/mcp/schema.go`、sourcecount `internal/mcp/schema.go` 同款）；CLI 侧 `internal/cli/schema.go` 只留入口归属（sourcecount `internal/cli/schema.go:3-4` 注释：「实际工具定义由 internal/mcp 通过 in-memory transport 导出，避免 CLI 与 MCP 维护两份契约」）。
4. **纯 CLI 命令（不映射 MCP 工具的）**：用 `jsonschema.For[RequestType]()` 直接反射输出该命令的输入/输出契约；`--flag --schema` 投影场景按标准 §5.5.1 动态导出 Sub-Schema 且零 I/O（`:390-392`）。
5. **不引入 invopop/jsonschema**（§4.3 对比结论），除非未来出现 `$ref` 控制/注释提取等进阶需求。

### 6.2 `--json` 输出契约（建议，全部有标准依据）

- 沿用现有 `{"ok":true,"data":...}` / `{"ok":false,"error":{"code","message"}}` 包络（标准 `:274-289`）；空列表输出 `[]` 而非 `null`；业务 JSON 错误写 stdout、诊断写 stderr、退出码仍反映失败。
- 退出码 0/2/1；`--help`/`--version`/`schema` 零 I/O（现状测试保留，`main_test.go:34-42`）。
- service 层错误统一为 `Error{Code,Message}`（不含退出码、不含 `isError`——标准 `:238-241`；sourcecount/glmquotawatch-gui 同款实现），替代现在 `err.Error()` 原文直传（`main.go:137` 等）。
- http API 复用同一包络（v2 标准明文「daemon API 的 JSON 设计沿用 v1 包络与投影规则」，`v2.md:145`；plansql 的裸 string Error 是应避开的偏差）。

## 7. 嵌入原生 html/css/js 的推荐做法

**推荐方案（建议，全部组件有实证）**：

```go
// internal/web/embed.go —— 照抄 liteconf 模式（职责注释 + 前缀剥离 + 防缓存）
//go:embed static
var staticFS embed.FS

func Handler() http.Handler {
    sub, _ := fs.Sub(staticFS, "static") // embed 路径编译期保证，运行时不会失败
    return noCache(http.StripPrefix("/ui", http.FileServerFS(sub)))
}
```

- 官方基础形态 `http.FileServer(http.FS(content))` + `StripPrefix`（<https://pkg.go.dev/embed>）；plansql 用 `fs.Sub + http.FS + http.FileServer` 挂根路径（`plansql/internal/web/embed.go:9-19`，挂载于 `daemon/server.go:102`）。
- liteconf 变体更值得抄的三点（`liteconf/internal/server/webui/webui.go:9-27`）：① `http.FileServerFS`（免 `http.FS` 适配）；② 子树挂载必须 `StripPrefix`，注释明言否则 `/ui/app.js` 会在子文件系统里找 `ui/app.js` 而 404；③ `noCache` 中间件「避免发版后持旧页面导致前后端不一致」。
- 挂载路由：`mux.Handle("GET /ui/", web.Handler())` 或挂 `/`（plansql 式，API 用 `/api/v1/` 前缀避开）；API 路由用 Go 1.22 方法路由（§4.2）。
- 页面端：原生 `fetch('/api/v1/...')`，无框架无构建步骤（plansql/liteconf 的 static 目录均为此形态：`index.html + app.js + style.css` 三件套）。
- **UI 风格备注（仅备注，不展开）**：用户长期偏好为浅色亮堂、绿色主色、圆角卡片风格（参照 CC Switch），反感暗色终端风与装饰性 gimmick；web 看板视觉应遵循此偏好。
- 注意 embed 排除规则：`static` 目录下避免放 `_`/`.` 开头文件，否则默认排除需 `all:` 前缀（§4.1）。

## 9. 推荐的 v3 目录结构与迁移要点

### 9.1 目录结构（建议；依据标准 `:554-556` 的 Go 组织方式 + 上述参考实现）

```text
go_projects/taskbarguard/
├── cmd/
│   └── taskbarguard/
│       └── main.go              # 组装入口：子命令分流 serve|list|run|config|set|apply|install-task|mcp|schema
```

## 10. 结论

用户提案的核心（service 包所有 + http/cli/mcp 薄壳 + web 走 http）与仓库现行标准完全同向，且每个部件在本仓都有已验证的参考实现：分层与契约抄 sourcecount，嵌入式 web 与 serve 抄 plansql/liteconf，托盘 GUI（若需要）抄 glmquotawatch-gui。v3 的架构选型建议锁定 **v1 直调形态**（单 exe、轻状态），daemon 化留待阶段二常驻守护需求落地时再评估。两个必须顺带修复的现状问题：数据目录违规（CWD `config.json`）与 `install-task` 的占位命令。`--schema` 全部改反射同源生成，依赖上零新增负担（google/jsonschema-go 已是 MCP SDK 传递依赖）。
