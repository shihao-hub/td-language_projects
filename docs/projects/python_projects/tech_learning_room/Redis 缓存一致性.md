# redis_cache_consistency —— 缓存一致性的五个经典现场

> 代码：`apps/redis_cache_consistency` ｜ 依赖：Redis ｜ 库：redis-py（asyncio）

## 一、这组实验解决什么问题

缓存不是「加一层 Redis」这么简单。三个失败模式（击穿 / 穿透 / 雪崩）、一个一致性窗口（失效竞态）、一个分布式系统入门题（分布式锁）——本组实验把五个现场逐一复现，并量化每个修复手段的收益。模拟的「数据库」用内存 dict + 300ms 延迟代替，**loader 调用次数就是打到数据库的请求量**，这是所有实验的核心观测量。

## 二、核心原理

### 2.1 cache-aside 与它的三个失败模式

cache-aside（旁路缓存）标准读写路径：

- 读：先 GET 缓存 → miss 则回源 DB → 回写缓存 + TTL；
- 写：更新 DB → **删除**缓存（不是更新缓存）。

三个失败模式全部发生在「miss 之后」：

| 模式 | 触发条件 | 解法 |
|---|---|---|
| 击穿 | **热点 key 恰好过期**，并发请求全部回源 | 合并回源（SET NX 单飞）或逻辑过期 |
| 穿透 | 查询**根本不存在**的数据，缓存永远 miss | 空值缓存（短 TTL）/ 布隆过滤器 |
| 雪崩 | **大量 key 同时过期**，瞬时回源洪峰 | TTL 随机抖动 / 多副本 / 熔断降级 |

三者区别只在一个维度：**「不命中」是因为过期、不存在、还是批量过期**。

### 2.2 失效竞态：先更新后删除仍会脏

标准写路径（更新 DB → 删缓存）存在一个著名窗口：

```
读 A：cache miss → 查 DB 得旧值 100（此刻还没回填）
写 B：更新 DB = 200 → DEL 缓存（此时缓存无 key，删除空转）
读 A：回填缓存 = 100                ← 旧值覆盖了新事实
结果：缓存 100 / DB 200，脏到 TTL 到期
```

工程补丁是**延迟双删**：写侧更新+删一次后，等待「一个在途读的完成时间」再删第二次，清掉迟到的回填。它不完美（延迟多长？删失败怎么办？），是「窗口收窄」而非「窗口消除」。

### 2.3 分布式锁的三层认知

1. **加锁一步到位**：`SET key token NX EX ttl`——`SETNX` + `EXPIRE` 两步会在客户端崩溃时留下永不过期的死锁；
2. **释放必须校验所有权**：锁的 value 放随机 token，释放用 Lua「GET==token 才 DEL」原子比较——否则业务超时后锁已易主，你的 DEL 会删掉别人的锁；
3. **锁是租约不是排他保证**：A 超时后 B 合法获得锁，但 A 的临界区还在跑——「同一时刻只有一个执行者」这个命题，Redis 锁只能给到「租约时间内」。需要真正互斥时用 fencing token（递增版本号由资源方仲裁），或者回到数据库唯一约束。

## 三、场景详解

### 场景 1：stampede —— 击穿与合并回源

朴素 cache-aside：热点 key 过期瞬间 20 个并发请求**全部**回源（DB 压力放大 20 倍）。合并回源版：第一个 miss 者用 `SET NX` 抢到回源权，其余人短暂轮询等待后直接读缓存——**只有 1 次回源**。

补充手段「逻辑过期」：值内嵌过期时间，过期后**返回旧值 + 异步刷新**，彻底消灭 miss 阻塞——适合「旧值可容忍」的场景（榜单、统计）。

### 场景 2：penetration —— 穿透与空值缓存

查询不存在的 id=999 十次，朴素逻辑十次全部打到 DB（None 不写缓存的后果）。空值缓存：把 None 也写进缓存（哨兵值 + **短 TTL**），之后被挡住。

两个边界：TTL 必须短（数据新建后别让空值挡太久）；写入侧新建数据后主动删对应空值 key。海量随机穿透（扫描攻击）用布隆过滤器前置。

### 场景 3：ttl-jitter —— 雪崩与抖动

100 个 key 固定 TTL=300s：`EXPIRETIME` 显示它们**集中在同一秒过期**（批量写入=批量失效）。加 ±60s 随机抖动后摊开成两分钟。批量预热任务尤其要加抖动。

### 场景 4：invalidate-race —— 失效竞态与延迟双删

按 2.2 的时序手动编排：裸奔版复现脏缓存（缓存 100 / DB 200）；延迟双删版在第二次删除后清掉迟到回填，下次读拿到 200。实验帮助你记住：**「先更新后删除」是标准写法但不是零窗口写法**。

### 场景 5：distributed-lock —— 误删、所有权与租约本质

阶段 A（无 token）：A 拿锁（TTL 1s）→ 业务超时锁过期 → B 获得新锁 → A 完成后无脑 DEL → **B 的锁被误删**，下一个申请者 C 将与 B 并发执行。

阶段 B（随机 token + Lua 比较删除）：A 完成时 Lua 校验 token 不匹配，B 的锁安然无恙。但注意：**A 的临界区代码此刻仍在执行**——这就是「租约不是排他」的现场。

## 五、面试高频问答

- **Q：缓存三大问题及解法？** A：击穿（单飞回源/逻辑过期）、穿透（空值缓存/布隆）、雪崩（TTL 抖动/多副本/熔断）。能说出三者「miss 原因不同」即是理解而非背诵。
- **Q：为什么是删缓存而不是更新缓存？** A：并发写时「更新缓存」会产生乱序覆盖（后写的旧值覆盖新值）；删除让下一次读触发回源，天然收敛。再问「先删后更新还是先更新后删」：先更新后删的窗口更小（删除前的读会回填新值）。
- **Q：Redis 分布式锁的坑？** A：三条：加锁一步（NX+EX）、释放校验 token（Lua）、锁过期后旧持有者仍在跑（fencing token / 最终以 DB 约束兜底）。提 Redlock 争议（Martin Kleppmann vs antirez）是加分项。
- **Q：延迟双删的延迟怎么定？** A：略大于「一次在途读的耗时」（回源+回填的 p99）；它只是缩小窗口，强一致需求走「订阅 binlog 失效」或版本号 CAS 回填。

## 六、生产对照（creativault）

生产侧滑动窗口限流（ZSET + Lua「先全检查后全写入」）与 API Key 租户缓存（120min TTL + 失败降级直查源）都是本篇机制的组合应用；延迟队列的 BLPOP 唤醒 + reclaim 租约回收（见 [redis-four-roles](Redis 四种角色.md)）则是「租约」思想在队列上的变体。
