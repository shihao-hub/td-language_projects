# billing_compensation —— 精确金额、幂等扣费、补偿配对与对账

> 代码：`apps/billing_compensation` ｜ 依赖：PostgreSQL ｜ 驱动：psycopg3（金额/事务时序直观）

## 一、这组实验解决什么问题

计费是后端里「错了会赔钱」的模块。它的三个永恒主题：**金额必须精确**（float 是事故）、**扣费必须幂等且原子**（重试/重放不能重复扣）、**扣了要能退**（业务失败触发补偿，且退款本身也要幂等）。本组实验搭一个最小但完整的积分账本：钱包 + 批次（lot）+ 不可变分录（entry），把六类机制逐一验证。

## 二、核心原理

### 2.1 金额：NUMERIC + Decimal，没有例外

二进制浮点无法精确表示十进制小数：`0.1 + 0.2 != 0.3`，10 万次累加 0.01 会凭空多出 0.000...x。单笔看不出来，**对账汇总时必然爆雷**（账平不了的经典根因）。规则：

- 数据库 `NUMERIC(p, s)`（如 `NUMERIC(20,6)`），Python `Decimal`，接口层 `condecimal`；
- 方向与绝对值分离：`direction ∈ {debit, credit}` + `amount` 恒正——「用负数表示支出」是金额审计里最危险的编码习惯。

### 2.2 幂等扣费：查-锁-扣三步一事务

```
事务开始
  1. 查 idempotency_key 已有成功分录 → 命中则直接返回首次快照（duplicate）
  2. SELECT ... FOR UPDATE 锁钱包行 → 余额校验（不足抛异常，零副作用）
  3. 钱包扣减 + 按批次消耗（lot.consumed 递增，耗尽的批次置 exhausted）+ 写 debit 分录
提交（任何一步失败整体回滚）
```

幂等键三键合一：`idempotency_key`（防重复）= `group_key`（补偿定位）= 业务任务标识。任务重试、消息重放、用户双击，全部被同一把锁挡住。

### 2.3 补偿配对：每个写方法都有「后悔药」

金钱状态的变更必须可逆。补偿不是「往钱包加钱」这么粗，而是**按原操作的镜像逆向**：

- 原 debit 分录按 `group_key` 定位动了哪些批次、各扣多少；
- 原批次 active → `consumed` 回补；exhausted → 恢复 active 再回补；**expired/不存在 → 新建补偿批次**（不复活过期批次、沿用原到期规则——账本历史不可变，也不因退款延长有效期）；
- 写 credit 分录，`related_group_key` 指回原操作，审计链路完整。

把补偿关系写成**显式数据结构**（charge→refund、grant→revoke 的配对表），而不是散落在注释里的口头约定。

### 2.4 重复退款防护

重试触发的第二次退款与首次并发/先后到达：靠补偿分录自身的幂等键 `refund:{原group_key}` 唯一约束兜底。**补偿自身的幂等常被忽略**——退一次可以，退两次不行。

### 2.5 不可变账本 + 对账

- 账本只 INSERT 不 UPDATE/DELETE（生产再加 DB 触发器 + 表权限双保险）；
- 定期对账：`SUM(credit) - SUM(debit) == wallet.balance`。配合不可变性，**任何代码 bug 都在对账时现形而非沉默**。

## 三、场景速览

| 场景 | 验证 |
|---|---|
| float-vs-decimal | Python/PG 双侧复现浮点误差；Decimal/NUMERIC 分毫不差 |
| idempotent-charge | 同 idem_key 第二次 charge → DuplicateRequest 带首次快照；余额只扣一次 |
| atomic-charge | 余额不足零副作用；扣减后故障 → 整事务回滚零残留 |
| refund-compensation | charge 30 元后业务失败 → refund：余额/批次/分录全部逆向恢复 |
| double-refund-guard | 第二次 refund 被唯一约束拦截 |
| reconcile | grant×2 + charge×3 + refund×1 之后账实守恒 |

## 五、面试高频问答

- **Q：金额为什么不能用 float/double？** A：二进制浮点无法精确表示十进制小数，误差在汇总/对账时放大。NUMERIC + Decimal + 接口层字符串传输（避免 JSON 解析转 float）。
- **Q：如何防止重复扣款？** A：幂等键唯一约束（数据库兜底）+ 前置查重（体验优化）+ 补偿配对（事后修复）。三层缺一不可，只有中间层会在并发下穿透。
- **Q：退款怎么设计？** A：按原操作精确定位（group_key），逐分录逐批次逆向；过期批次新建补偿批次而非复活；退款自身幂等（refund:原键 唯一）。
- **Q：账实不平怎么排查？** A：先对账定位差值（哪个用户、哪段时间）→ 查该区间分录与事务日志 → 常见根因：绕过账本的直接 UPDATE、非原子双写、float 精度。
- **Q：批次（lot）是什么？为什么需要？** A：积分/额度带有效期与来源（充值/赠送），按批次管理才能回答「这批什么时候过期」「退款退到哪批」。扣减按 FIFO/优先级消耗批次，补偿按原批次回补。

## 六、生产对照（creativault）

生产计费 v2（billing_v2）是本篇的完整形态：DDL 层 `CHECK (direction in ...)` 与 `amount > 0`、`credit_entry` 触发器禁改禁删、`COMPENSATION_PAIRS` 显式配对表、L1/L2/L3 三层数据库幂等（快路径查快照 / 唯一约束竞争插入 / FOR UPDATE 行锁裁决）、outbox 事件与状态同事务。教学版保留主干判断力，省略多币种、冻结额度与对账任务编排。
