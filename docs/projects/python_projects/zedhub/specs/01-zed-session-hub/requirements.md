# 需求文档

## Summary

将 `python_projects/zedhub` 建设为统一的 Zed 与本地 AI agent 会话工具，当前吸收
OpenCode 相关能力以及 `go_projects/ocstat` 的稳定能力，形成一个 Python 项目，提供
会话检索、完整内容查看、模型与 effort 统计、导出、补登以及跨机器迁移能力。

当前只实现 OpenCode 数据源，但公共会话概念、结果契约和扩展边界必须能够容纳未来的
Pi agent、Claude Code、Codex、Antigravity 等数据源，不得把 OpenCode 的字段和行为未经
区分地定义为所有 agent 的通用事实。

统一项目继续使用 `zedhub` 名称。现有 `zedhub` 的 CLI、JSON-RPC 和 MCP 能力需要保持
兼容；新增能力不得通过运行时依赖另外两个旧项目实现。

新的自动化接口以 CLI 的 `--json`、MCP 和按需使用的 WebSocket 为主。现有
`zedhub rpc` 作为兼容入口保留，但不作为新增业务能力必须同步建设的第三套接口。
WebSocket 本阶段只提供最小只读骨架，不要求覆盖全部业务能力。

## Functional Requirements

### FR-1 统一会话查询

系统必须同时支持以下两类对象的查询：

- Zed 会话索引：thread、项目路径、agent、归档状态、标题和时间信息；
- OpenCode 会话：session 元数据、消息和消息内容片段。

系统必须能够通过关联的 `session_id` 查询 Zed 索引与 OpenCode 会话之间的关系，且不能
因为某一侧缺少记录而伪造另一侧的数据。

### FR-2 Zed 会话检索与统计

系统必须保留现有 `zedhub` 的 Zed 查询能力，包括：

- 按项目路径、agent、归档状态、时间范围和关键词筛选会话；
- 查询单个 Zed thread；
- 按项目统计会话；
- 汇总会话总数、活跃数、归档数、agent 分布、项目数、工作区组合和月度活动。

### FR-3 OpenCode 会话内容

系统必须提供 OpenCode 会话列表和详情查询能力，包括：

- session 标识、标题、目录、agent、模型和时间信息；
- message 的角色、agent、模型和时间信息；
- message 下的内容片段及其类型、文本和时间信息；
- 对不存在的 session 返回稳定的未找到错误，而不是空成功结果。

### FR-4 启动模型与 effort 统计

系统必须提供 OpenCode 会话的模型与 effort 统计能力，包括：

- 按 provider、model 和 effort/variant 分组统计会话数及占比；
- 在可用数据完整时，根据首条非 title 的 assistant 消息还原会话启动时实际生效的模型；
- 支持 `model.variant` 以及模型配置中的 `reasoningEffort` / `effort`；
- 对缺失配置、无法解析配置和数据库结构不完整情况给出可识别的降级状态；
- 支持一次性统计和定时刷新统计。

统计结果必须区分“启动模型”与“当前模型”，不得在启动模型不可还原时无标记地将当前
模型当作启动模型。

### FR-5 会话导出

系统必须支持将单个或指定范围内的会话导出为结构化数据和 Markdown，导出内容至少
包括会话元数据、消息和可导出的文本内容。

系统必须支持把指定项目范围内的 Zed/OpenCode 会话导出为可迁移的 SQLite 归档文件，
并记录归档元数据和导出数量。

### FR-6 会话补登

系统必须支持将 OpenCode 中存在但 Zed 尚未建立索引的会话补登到 Zed。

补登必须具备以下行为：

- 默认只生成 dry-run 计划，不修改数据库；
- 只有显式提供 `--apply` 才允许写入；
- 已经存在于 Zed 的 session 必须幂等跳过；
- 支持项目路径匹配、多个目录消歧、统一目标目录和是否包含子会话；
- 写入失败时不得宣称补登成功。

### FR-7 跨机器导入

系统必须支持从归档 SQLite 文件导入会话到另一台机器的 Zed/OpenCode 数据库。

导入必须支持：

- 读取归档并展示导入计划；
- 默认 dry-run；
- 显式 `--apply` 后才执行实际写入；
- 保留目标机器已有数据，不以覆盖方式删除现有会话；
- 在必要时重新生成目标数据库要求的标识并重写相关关联；
- 导入前备份目标数据库；
- 写入后重新读取并验证导入结果；
- 目标 schema、目标目录或进程状态不满足要求时拒绝执行并说明原因。

### FR-8 多入口一致性

系统必须提供以下入口能力：

- CLI：查询类命令默认提供人类可读输出，并提供稳定的 `--json` 输出；
- MCP：第一阶段提供只读查询、内容查看和统计能力；
- JSON-RPC：保留现有 `zedhub rpc` 的程序化查询能力，作为兼容入口；新增业务能力不要求
  自动增加对应的 RPC 方法；
- WebSocket：提供最小 JSON 消息通信骨架。本阶段默认支持两个只读操作：`threads.list`
  和 `stats`；不要求与 CLI、MCP 或完整业务核心完全覆盖；
- `schema`：导出与实际 MCP 注册定义同源的静态契约；
- `--help` 和 `--version`：不连接业务数据库、不执行写操作。

数据库写入能力，包括补登和归档导入，第一阶段只通过 CLI 提供，并要求明确的
`--apply` 参数。写操作暂不作为 MCP 或 WebSocket 功能暴露。

### FR-9 兼容现有 zedhub

现有 `zedhub` 的以下公开行为必须保持兼容，除非另有迁移说明：

- 线程、项目和总览统计的业务含义；
- 已有 JSON-RPC 方法和错误语义；新增业务能力不承诺提供 RPC 等价方法；
- MCP 只读工具的业务结果；
- `--db` 等已有数据库路径参数；
- 成功、空结果、参数错误和运行错误的区分。

旧项目的代码不作为新项目的运行时依赖。旧项目可以在迁移完成后进入弃用或归档状态。

### FR-10 面向多 agent 的扩展边界

系统必须将 agent 类型或数据源作为会话数据的一部分进行识别。公共查询和统计结果必须
能够区分通用字段与 agent 专属字段：

- 通用字段的语义不能依赖 OpenCode 的专有表名、ID 格式或 JSON 字段；
- agent 专属字段可以在对应数据源可用时返回，但缺失时必须标记为不可用，不能填充猜测值；
- 当前未实现的数据源不得被伪装成 OpenCode，也不得出现在“已支持”的能力清单中；
- 新增 Pi agent、Claude Code、Codex 或 Antigravity 数据源时，不能破坏已有 OpenCode 查询、
  统计、导出和迁移结果。

本次不实现上述未来数据源，但需求、错误和结果契约必须为后续接入保留明确边界。

## Non-Functional Requirements

### NFR-1 数据安全

读取 Zed 和 OpenCode SQLite 时必须考虑 WAL sidecar 数据。读取不能破坏正在运行的
Zed 或 OpenCode 进程。

所有数据库写入操作必须具备明确的 dry-run 与 apply 边界，并在写入前检查相关进程状态、
在可行时创建备份、使用事务、完成 WAL 处理并执行写入后验证。当前已实现的数据源为 Zed
和 OpenCode；未来新增 agent 数据源时，必须单独声明其读取快照、写入、备份和恢复语义，
不能默认套用 OpenCode 的数据库行为。

### NFR-2 schema 变化

Zed 和 OpenCode 的数据库 schema 均视为可能变化。缺少必需表或字段时，系统必须：

- 对可以安全降级的只读统计给出明确降级结果；或
- 对无法保证数据正确性的操作拒绝执行并返回可诊断错误。

系统不得依赖 `SELECT *`，所有 SQL 查询必须显式列出字段。

### NFR-3 入口与核心解耦

CLI、MCP、WebSocket 和现有 JSON-RPC 兼容入口必须调用同一套业务核心，不得分别实现会话
筛选、统计、导出、补登或导入流程。新增业务能力至少由 CLI 或 MCP 暴露；WebSocket 和兼容
RPC 只按已声明的能力范围提供，不要求入口之间完全对称。

入口层负责参数解析、协议适配和输出渲染；数据库访问、业务校验、写入编排、错误分类
和结果模型属于公共核心。

### NFR-4 本地运行环境

项目必须继续支持 Windows + PowerShell + `uv` 的主要运行方式，并使用 Python 3.12
或更高版本。

项目自身运行时产生的数据库、备份、缓存、锁和日志等数据必须遵守仓库约定，写入
`%APPDATA%\language_projects\zedhub\`；未设置 `APPDATA` 时回退到
`~/.language_projects/zedhub/`，并在写入前创建完整目录链。

### NFR-5 可诊断性

所有失败结果必须区分至少以下类别：参数错误、数据源不存在、schema 不兼容、记录未找到、
进程仍在运行、写入失败、验证失败和结果未知。

人类输出可以包含诊断信息；JSON、RPC 和 MCP 结果必须提供稳定的错误类别和可公开说明，
不得将内部堆栈或敏感路径信息作为唯一错误契约。

### NFR-6 多 agent 扩展兼容性

公共会话模型和接口契约必须优先表达跨 agent 都成立的概念，例如数据源、agent 类型、会话
标识、标题、目录、时间、模型和消息；不得把某一 agent 的数据库表结构直接暴露为公共领域
契约。

对于 agent 专属能力，系统必须能够表达“未支持”“数据源不可用”和“该 agent 不提供”
等不同状态，不能统一降级为空字符串、零值或伪造的 OpenCode 结果。新增数据源的接入应
局限在其数据读取、解析和能力声明范围内，不得要求修改已有 agent 的业务语义。

### NFR-7 WebSocket 初版安全边界

WebSocket 初版默认只允许本机回环地址访问，不承担公网服务、身份认证或跨机器安全接入
职责。连接处理必须有明确的关闭和错误行为，不能因客户端断开而遗留数据库连接、快照文件
或后台任务。

WebSocket 使用 JSON 文本消息承载请求和响应；具体字段和握手细节在设计文档中锁定。未
声明支持的操作必须返回明确的“不支持”错误，不得静默忽略请求。

## Acceptance Criteria

### AC-1 统一只读查询

当用户只安装并运行统一后的 `zedhub` 项目时，用户能够分别查询 Zed thread、OpenCode
session、完整会话内容、项目统计和总览统计；这些能力不需要安装或调用
`zed-opencode-sessions` 或 `ocstat`。

### AC-2 Zed 查询兼容

当使用现有 `zedhub` 的线程、项目和总览查询参数时，统一项目返回的业务结果、排序和
错误类别与迁移前一致；空数据库结果仍然是成功的空结果。

### AC-3 OpenCode 内容正确关联

当一个 session 同时存在于 OpenCode 数据库和 Zed 索引时，查询结果能够通过同一个
`session_id` 关联两侧数据；当任意一侧缺失时，结果明确标记缺失，不生成虚假的关联记录。

### AC-4 启动模型口径正确

当 OpenCode 数据库包含首条非 title assistant 消息以及对应的 session 事件时间线时，
统计结果使用该消息时间点生效的模型和 variant；当事件或消息数据不可用时，结果标记
为降级并说明使用的是当前模型或无法统计启动模型。

### AC-5 effort 配置合并正确

当模型 variant 缺失或为 `default`，且 OpenCode 配置中存在该模型的
`reasoningEffort` 或 `effort` 时，统计结果能够区分原始 variant 与配置解析出的实际 effort；
配置文件不存在或解析失败不会导致其他可用统计整体失败。

### AC-6 所有写操作默认安全

当用户执行补登或归档导入而未提供 `--apply` 时，系统只读取数据并输出计划，不修改
Zed、OpenCode 或项目内部数据库；提供 `--apply` 后，如果进程检查、备份、schema 检查或
前置校验失败，系统在写入前终止。

### AC-7 写入结果可验证

当补登或归档导入成功完成时，系统已经完成事务提交、必要的 WAL 处理和只读复查，并能
报告实际写入数量；当复查结果与计划不一致时，系统不得返回成功状态。

### AC-8 归档可迁移

当用户在源机器导出指定项目的归档文件，并在目标机器先执行 dry-run 再执行 `--apply` 时，
归档中的会话能够被导入到目标目录，同时保留目标机器原有会话，且导入后的 Zed 索引与
OpenCode session 关联可被重新查询。

### AC-9 多入口结果一致

对现有 RPC 已支持的同一份只读数据和相同业务参数，CLI `--json`、JSON-RPC 和 MCP 返回的
核心业务字段、排序和错误类别一致；新增业务能力至少保证 CLI `--json` 与 MCP 的结果一致。
入口可以使用不同的展示包装，但不得各自维护不同的业务筛选和统计规则。

### AC-10 契约可离线发现

执行 `zedhub schema` 时，即使 Zed 或 OpenCode 数据库不存在，也能输出可解析的 JSON 契约；
输出中的只读 MCP 工具名称、输入约束、输出约束和行为标注与实际注册定义一致。

### AC-11 数据库结构变化可控

当 Zed 或 OpenCode 数据库缺少必需表或列时，系统不会因未捕获异常崩溃或产生无依据的统计；
可安全降级的命令返回带降级说明的结果，不可安全降级的命令返回稳定的 schema 错误。

### AC-12 旧项目可退出运行时链路

统一项目完成后，执行任意统一项目能力不需要导入 `zed-opencode-sessions` 的 Python 包，
也不需要启动或调用 `ocstat.exe`；旧项目只作为迁移参考或兼容过渡存在。

### AC-13 未实现 agent 的边界清晰

当用户查询 Pi agent、Claude Code、Codex 或 Antigravity 数据时，如果对应数据源尚未实现，
系统必须返回明确的“数据源未支持”状态或错误，不得把结果当作 OpenCode 数据返回，也不得
静默返回看似成功的空结果。

### AC-14 OpenCode 结果不锁死未来扩展

在当前 OpenCode 能力实现后，公共会话查询、统计和导出结果中能够识别数据源及 agent 类型；
OpenCode 专属字段不会被无标记地当作所有 agent 都具备的必填字段。未来增加另一数据源时，
已有 OpenCode 调用的字段语义和成功/失败行为保持不变。

### AC-15 WebSocket 最小能力可用

启动 WebSocket 入口后，客户端能够建立连接，并通过 JSON 文本消息调用 `threads.list` 和
`stats` 两个只读操作，收到可解析的成功响应；参数错误、数据库错误和未声明操作能够收到
可区分的错误响应。

WebSocket 返回的业务数据必须来自现有公共核心，与相同输入下 CLI `--json` 的核心数据一致。
客户端断开后，服务端能够释放本次请求的数据库连接和临时资源。

### AC-16 WebSocket 不越权

通过 WebSocket 发送补登、归档导入或其他未声明的写操作时，系统必须拒绝请求，不修改 Zed、
OpenCode 或项目内部数据。

## Out of Scope

- 本次不开发 Web UI、桌面 GUI 或远程 HTTP 服务。
- 本次不要求 WebSocket 覆盖全部 CLI、MCP 或 JSON-RPC 能力；初版只实现 `threads.list` 和
  `stats` 两个只读操作。
- 本次不为 WebSocket 实现公网部署、身份认证、跨机器安全接入或复杂连接管理。
- 本次不修改 OpenCode 或 Zed 的上游数据库 schema。
- 本次不实现 Pi agent、Claude Code、Codex 或 Antigravity 的数据源接入；本次只定义兼容它们
  的公共边界与扩展要求。
- 本次不删除 Zed 或 OpenCode 中已有的会话数据。
- 本次不把数据库写入能力暴露为 MCP 或 WebSocket 功能；后续是否开放另行评估。
- 本次不保证跨版本数据库导入对所有未来 Zed/OpenCode 版本永久兼容；遇到未知 schema
  必须拒绝或降级，而不是猜测字段含义。
- 本次不在 `go_projects/ocstat` 中继续扩展功能；Go 项目的归档或弃用属于独立迁移事项。
- 本次不要求立即删除旧项目或立即改变旧命令名称；兼容迁移完成后再处理生命周期。
