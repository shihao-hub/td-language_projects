# taskmon 源码阅读三方法/code-reading-methods

> 目的：把"走马观花看代码"升级为带提取动作的主动学习，用最小成本换最大留存。
> 对应两个学习目标：学会从零写这类 TUI 工具（能力），以及把 TypeScript 练熟（语言）。
> 使用约定：方法一、方法三的 taskmon 答案分别封在附录 A / 附录 B，**先自己做，再翻附录**。

---

## 0. 总纲：为什么会"看了没印象"

记忆的深浅取决于**提取（recall）的强度**，而不是输入的次数。

- 走马观花 = 认得出（recognition）：信息只进工作记忆，合上代码就还原不出来，还伴随"我懂了"的流畅感错觉。
- 手工复刻 = 100% 提取：最牢但最贵，而且 1:1 抄一般代码会把平庸写法一起内化。
- 下面三个方法 = 在不同粒度上制造"部分提取"，各测一层东西：

| 方法 | 提取粒度 | 成本 | 测什么 |
|---|---|---|---|
| 方法三：凭记忆画数据流 | 全局结构 | 10 分钟 | 架构进没进脑子 |
| 方法一：预测式阅读 | 单函数 / 单模块 | 精读的约三成 | 细节理解 + 盲区 |
| 方法二：改造式重写 | 整个系统 | 2-3 次 × 2 小时 | 设计与再造能力 |

推荐顺序：**三 → 一 → 二**（先暴露盲区，再局部精读，最后整体重造），文末有组合训练计划。

## 1. 方法一：预测式阅读

### 1.1 原理

读代码时的"懂了"大多是流畅感错觉——没有提取动作把信息钉进长期记忆。预测强迫你在看答案之前先自己生成一遍实现，**猜错时的惊讶感是记忆的粘合剂**（认知科学里叫 testing effect / generation effect：自己生成过的内容，记得远比读过的牢）。

### 1.2 操作步骤

1. **只看接口，不看实现**：先只读 `src/types.ts` 和各文件的导出签名（如 `splitCsvLine(line: string): string[]`），函数体不打开。
2. **动笔写预测**（脑子里的"我猜大概是"太软，必须落字）。每个函数预测三件事：
   - 输入的边界情况有哪些？
   - 换成我，会怎么实现？
   - 预计会在哪里踩坑？
3. **打开实现对照打分**：
   - ✓ 猜对 → 已会，永远不用再看
   - ✗ 猜错 → 学习点，精读
   - ? 作者处理了我没想到的情况 → 最大学习点，重点精读
4. **只精读 ✗ 和 ?**：精读范围会自动压缩到 20-30%。

### 1.3 使用示范：用 `formatBytes` 走一遍全流程

（声明：这个函数为做示范被剧透，所以它**不在**后面的练习题里。）

**Step 1：只看签名和注释**

```ts
/** 字节数人性化显示：1024 进制，按量级自适应小数位 */
export function formatBytes(bytes: number): string;
```

**Step 2：动笔写预测**（示范写作格式，建议就写在草稿或代码注释里）

```
- 边界：0？负数？NaN/Infinity？恰好 1023 / 1024？大到超出单位表（>TB）？
- 我的实现：while 除以 1024 换单位，小数固定 1 位（"1.5 MB"这种）
- 预计的坑：单位表数组越界；除完显示 "1024.0 KB" 这种换算临界问题
```

**Step 3：打开实现对照**（`src/format.ts:40-51`）

```ts
export function formatBytes(bytes: number): string {
  if (!Number.isFinite(bytes) || bytes <= 0) return '0';
  const units = ['B', 'KB', 'MB', 'GB', 'TB'];
  let v = bytes;
  let u = 0;
  while (v >= 1024 && u < units.length - 1) {
    v /= 1024;
    u++;
  }
  const dec = v >= 100 ? 0 : v >= 10 ? 1 : 2;
  return `${v.toFixed(dec)} ${units[u]}`;
}
```

**Step 4：逐条打分，产出精读清单**

| 我的预测 | 实际 | 分类 | 动作 |
|---|---|---|---|
| while 除以 1024 换单位 | 一致 | ✓ | 跳过 |
| 小数固定 1 位 | 按量级自适应：>=100 取 0 位，>=10 取 1 位，否则 2 位 | ✗ | 精读这一行 |
| NaN / Infinity | 开头有 `!Number.isFinite` 守卫 | ? | 记住这个防御套路 |
| 单位表越界 | `u < units.length - 1` 封顶在 TB | ? | 记住封顶写法 |

产出：这个函数 12 行，真正要精读的只有 2 行，其余确认已会。**这就是本方法的产出物——一张压缩过的精读清单，而不是"我全看过了"的感觉。**

### 1.4 taskmon 练习题（做完前不要翻附录 A）

- **Q1 tasklist 解析**：先在终端跑 `tasklist /fo csv /nh`（建议重定向到文件细看）。然后预测：内存列的确切格式和坑？进程名含逗号时 CSV 如何表示、解析器要处理什么？输出编码是什么、现在的代码处理了吗？（对照 README「已知限制」第二条和你自己留的 sh-note）
- **Q2 ANSI 原地刷新**：README 说"原地刷新无闪烁"。先查 `\x1b[H`、`\x1b[K`、`\x1b[2J` 三个转义序列各自的含义，再猜：怎么不清屏地整屏替换 40 行？
- **Q3 定时器与按键的竞态**：定时刷新（tick → setTimeout → tick 链）和按键事件回调都在改同一批状态。预测会出什么问题？再看代码防没防。
- **Q4 displayWidth**：`format.ts` 为什么需要 `displayWidth` 而不是直接 `s.length`？什么场景下两者不相等？

## 2. 方法二：改造式重写

### 2.1 原理

复刻的目标是"像"——照着参考答案抄，代码一般你也抄进去了；改造式的目标是"对"——先交卷再批卷。参考答案不完美没关系，**批改行为本身就在训练判断力**，"代码一般"反而让参考答案更有批改价值。

### 2.2 操作步骤

1. **纸面重新设计**（半小时封顶）：假装没见过代码，只凭下面这句需求写出模块划分、类型定义、数据流。
2. **实现核心**（真写代码，见 2.4 范围与时间盒）。
3. **逐文件 diff 批改**，每处分歧归三类（见 2.3 示范）。
4. **把"我更好"真的落地**：这是自己的仓库，替换后跑 `pnpm test` 验证行为没变——学习变成真实工程产出。
5. **加分项：修一个真 bug**——中文进程名乱码（README 已知限制，tasklist 输出是 OEM 编码而代码未解码），正好就是你在 sh-note 里好奇的"版本问题"。

重新设计用的需求题面（只凭这个，不看原码）：

> Windows 控制台实时显示进程内存占用：同名进程分组（组间按总内存降序、组内按单进程降序），默认折叠、可展开收起，原地刷新无闪烁，上下键移动光标、q 退出，支持 --once 单帧输出。

### 2.3 使用示范：三类分歧的批改格式

（前提：假设你已独立写完自己的版本。以下是格式示范，真正的收获来自你自己 diff 时产生的分歧。）

**例 A「我没想到」→ 吸收**

视口跟随（`src/main.ts:113-119`）：每次 draw() 先把 cursor 钳制进合法范围，再保证光标行落在视口 `[offset, offset+body)` 内——光标在视口上方就把 offset 拉上来，在下方就推下去。初写 TUI 的人通常只想得到"按键移动光标"，想不到"光标行必须始终可见"这层约束（按 End 跳到最后时尤其明显）。
动作：理解后记入个人套路库。

**例 B「作者更好」→ 采纳**

`Frame.groupRows`（`src/render.ts:20-24`）：renderFrame 是纯函数，但顺手返回 groupRows——"第 i 个可见组在第几行"的映射在生成行的同时就记下来，main 的光标 / 滚动逻辑直接查这张表。如果自己写，多半会在 main 里按展开状态重算行号，等于把 render 的逻辑复述一遍，两处会漂移。
动作：采纳为个人模板，下次写 TUI 直接用。

**例 C「我更好」→ 落地**

- `src/main.ts:27-39`：11 个模块级可变全局变量，状态散落、无归属
- `src/main.ts:242`：End 键用 `Number.MAX_SAFE_INTEGER` 当"跳到最后"的 hack，靠 draw() 里的钳制收敛
- `draw()`（`src/main.ts:104-131`）：一个函数混了光标钳制、视口跟随、切片、滚动提示、ANSI 输出五个职责

动作：重写时把状态收进一个 state 对象（或闭包），拆分 draw()；替换后跑 `pnpm test`（vitest，`src/__tests__/` 已有 4 个测试文件覆盖 grouping / format / render / tasklist）验证行为不变。

### 2.4 范围与时间盒

- **重写**：tasklist 解析、grouping、render 帧生成、main 的刷新-交互循环（核心四件）
- **可跳过**：`scripts/build-exe.ts`、release / tag 流程、commander 参数解析（练手重点不在 CLI 库，最简 `process.argv` 即可）
- **时间盒**：2-3 次 × 2 小时。写不完也停，剩下的部分对照原码看完差异即收获

## 3. 方法三：凭记忆画数据流

### 3.1 原理

最便宜的自测：10 分钟、零代码，测的是"全局结构"进没进脑子。走马观花最容易漏的恰恰是结构——每个函数单看都懂，连起来一片空白。

### 3.2 操作步骤

1. **关掉所有代码**，拿纸或空白文本文件。
2. **画流水线**：方框 = 处理阶段，箭头 = 数据流。关键规则：**每根箭头必须标出流过数据的形状**（不是"数据"，而是 `ProcessInfo[]` 这种具体类型）。标不出形状 = 没真记住，那就是精读目标。
3. 每个方框标注：**哪个文件哪个函数**负责它。
4. **补支线**：错误路径？`--once` 单帧模式？按键事件从哪进来、改了什么状态、怎么影响下一帧？窗口 resize 呢？支线画不出很正常——走马观花最漏的就是它们。
5. **打开代码批改**：漏的箭头、错的形状、忘的支线 = 精读清单。三天后重画一次（间隔重复），全对即毕业。

### 3.3 使用示范（中性小例子，练手用）

题目：凭记忆画一个"统计日志中各 IP 出现次数"脚本的数据流。

```
读文件 ──→ 按行拆分 ──→ 提取 IP ──→ 计数 ──→ 排序 ──→ 格式化打印
string     string[]      string      Map     [ip,n][]    string
(整个文件)  (每行一个)   (每行一个)  <string,
                         number>
```

批改表格式：

| 我画的 | 实际代码 | 结论 |
|---|---|---|
| 主线 6 个阶段 | 一致 | ✓ 跳过 |
| 没画"格式错误行跳过"分支 | 有 continue 跳过 | 漏支线 → 精读 |
| 计数形状标的是 `object` | 实际是 `Map` | 形状不准 → 精读 |

## 附录 B：taskmon 数据流参考答案（先自己画完再看）

**主线（每轮 tick 走一遍，共 4 次变形、5 种形状）：**

```
tasklist /fo csv /nh
(子进程 stdout，OEM 编码的 CSV 文本)                    string
        │
        ▼
parseTasklistCsv  [src/tasklist.ts:49]（内用 splitCsvLine + parseMemField）
        │                                            ProcessInfo[] {name,pid,memBytes}
        ▼
groupProcesses  [src/grouping.ts:8]
        │                                            ProcessGroup[]（组内/组间两级降序）
        ▼
renderFrame(groups, opts)  [src/render.ts:48]
        │                                            Frame {lines: string[], groupRows: number[]}
        ▼
draw()  [src/main.ts:104]（视口切片 + 光标钳制/跟随 + 滚动提示）
        │                                            单个 ANSI string（定位+清行序列拼成）
        ▼
stdout.write
```

**支线：**

| 支线 | 路径 |
|---|---|
| 按键线 | stdin keypress（`src/main.ts:203`）→ 改 cursor / expandedNames → 直接调 draw()（用缓存的 groups，**不重新采集**） |
| 定时线 | tick() 末尾 setTimeout 自排下一轮（`src/main.ts:69-73`）；空格键 refreshNow（`:175`）clearTimeout 后立刻 tick |
| 错误线 | listProcesses 抛错 → error 字符串 → currentFrame() 生成错误帧（`src/main.ts:76-88`）→ draw() |
| 单帧线 | `--once` 或非 TTY（`src/main.ts:263`）→ 采集 → renderFrame(expandAll) → console.log → exit，不进交互循环 |
| resize 线 | stdout 'resize'（`src/main.ts:285`）→ draw() |

**两问答案**：形状变 4 次（string → ProcessInfo[] → ProcessGroup[] → Frame → string）；两条线汇合在 draw()，共享的是模块级可变全局状态（groups / cursor / offset / expandedNames…）——这也正是 Q3 竞态题的病灶所在。
